# 기능 설계 가이드라인

## 1. 설계 원칙

### 1.1 기존 코드와의 일관성
- 기존 아키텍처 패턴을 따르세요
- 네이밍 컨벤션을 유지하세요
- 유사한 기능의 구현 방식을 참고하세요

### 1.2 최소 영향 원칙
- 기존 코드 수정을 최소화하세요
- Breaking changes를 피하세요
- 점진적 변경을 선호하세요

### 1.3 테스트 가능성
- 테스트하기 쉬운 구조로 설계하세요
- 의존성 주입을 활용하세요
- 모킹이 가능한 인터페이스를 사용하세요

### 1.4 확장 가능성
- 향후 확장을 고려하되 과도한 추상화는 피하세요
- YAGNI (You Aren't Gonna Need It) 원칙을 기억하세요
- 단순함을 유지하세요

## 3. 설계 패턴 선택 가이드

### 생성 패턴 (Creational)
- **Factory**: 객체 생성 로직을 분리할 때
- **Builder**: 복잡한 객체 생성 시
- **Singleton**: 전역 상태/리소스 관리 시 (주의해서 사용)

### 구조 패턴 (Structural)
- **Adapter**: 기존 인터페이스와 호환 시
- **Facade**: 복잡한 서브시스템 단순화 시
- **Decorator**: 동적으로 기능 추가 시

### 행동 패턴 (Behavioral)
- **Observer**: 이벤트 기반 통신 시
- **Strategy**: 알고리즘 교체가 필요할 때
- **Command**: 작업 실행/취소 필요 시

## 4. Brownfield 프로젝트 특별 고려사항

### 레거시 코드와의 공존
- 레거시 코드를 래핑하여 새 인터페이스 제공
- 점진적 마이그레이션 계획 수립
- 기존 테스트 유지 및 확장

### 기술 부채 관리
- 새 기능 추가 시 관련 기술 부채 식별
- 리팩토링 범위 제한
- 별도의 기술 부채 해소 작업으로 분리

### 하위 호환성
- API 버저닝 고려
- 데이터베이스 마이그레이션 전략
- 점진적 롤아웃 계획
