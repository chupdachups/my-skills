# 코드 리뷰 가이드라인

Google Engineering Practices 기반 코드 리뷰 원칙

## 핵심 원칙

### 1. 코드 품질 향상이 목표
- 코드베이스의 전반적인 건강 상태를 개선
- 완벽함보다는 지속적인 개선에 집중
- 리뷰어는 교사가 아닌 동료로서 피드백 제공

### 2. 리뷰어의 책임
- 변경사항이 시스템을 개선하는지 확인
- 버그, 성능 문제, 보안 취약점 식별
- 코드 가독성과 유지보수성 평가

### 3. 작성자의 책임
- 변경사항을 명확하게 설명
- 리뷰어의 시간을 존중하는 적절한 크기의 CL
- 피드백을 열린 마음으로 수용

## 리뷰 체크포인트

### 설계 (Design)
- [ ] 변경사항이 시스템에 적합한가?
- [ ] 올바른 추상화 수준인가?
- [ ] 기존 코드와 잘 통합되는가?

### 기능 (Functionality)
- [ ] 코드가 의도한 대로 동작하는가?
- [ ] 엣지 케이스가 처리되었는가?
- [ ] 에러 처리가 적절한가?

### 복잡도 (Complexity)
- [ ] 코드가 필요 이상으로 복잡하지 않은가?
- [ ] 다른 개발자가 이해하기 쉬운가?
- [ ] 과도한 엔지니어링이 없는가?

### 테스트 (Tests)
- [ ] 적절한 테스트가 포함되었는가?
- [ ] 테스트가 올바르고 유용한가?
- [ ] 테스트 커버리지가 충분한가?

### 네이밍 (Naming)
- [ ] 변수, 함수, 클래스 이름이 명확한가?
- [ ] 이름이 의도를 잘 전달하는가?

### 주석 (Comments)
- [ ] 필요한 곳에 주석이 있는가?
- [ ] 주석이 "왜"를 설명하는가?
- [ ] 불필요한 주석은 없는가?

### 스타일 (Style)
- [ ] 프로젝트 스타일 가이드를 따르는가?
- [ ] 일관성이 유지되는가?

### 문서화 (Documentation)
- [ ] README나 문서 업데이트가 필요한가?
- [ ] API 문서가 업데이트되었는가?

## 리뷰 수준별 집중 영역

### Quick Review
- 명백한 버그
- 보안 취약점
- 스타일 위반

### Standard Review
- Quick Review 항목 전체
- 설계 적합성
- 테스트 품질
- 코드 복잡도

### Thorough Review
- Standard Review 항목 전체
- 성능 영향 분석
- 확장성 고려
- 문서화 완전성
